# 카테고리·세부 종류 변경 시 임시 입력 정리 — 2026-11-09

## 원인과 적용 범위

이전 UX는 기존 사용자 지정 값을 보호하기 위해 `category`만 변경하고 세부 종류·핏 컨트롤러는 그대로 두었다. 설명·일러스트는 즉시 바뀌었지만 새 분류와 맞지 않는 입력값까지 남았다. 초기 데이터 로딩과 사용자의 명시적인 분류 변경을 같은 보존 규칙으로 처리한 것이 원인이다.

`GarmentEditorScreen`은 일반 IndexedDB 옷장과 서버 개발 옷장이 함께 사용한다. 이번 수정은 화면의 임시 상태 전환만 다루며 저장소·데이터 모델·직렬화·Supabase DTO·revision 정책을 바꾸지 않는다.

## 필드별 유지·초기화 기준

| 항목 | 분류 변경 시 처리 |
| --- | --- |
| 세부 종류 | 새 카테고리의 기존 추천 목록에 있는 값은 유지. 다른 카테고리의 추천 종류와 호환성을 확정할 수 없는 사용자 지정 값은 초기화 대상으로 안내 |
| 핏 | 정리된 세부 종류를 기준으로 새 핏 추천에 포함되는 값은 유지. 맞지 않는 표준 핏과 호환성을 확정할 수 없는 사용자 지정 핏은 초기화 대상 |
| 신발·가방·액세서리·기타의 기존 핏 | 해당 카테고리에 추천이 없으므로 분류 변경 시 초기화 대상. 해당 화면에서 사용자가 새로 직접 입력하는 기능은 계속 제공 |
| 이름 | 유지. 종류를 바꿔도 자동으로 이름을 변경하지 않음 |
| 대표·추가 색상, 계절, 스타일 태그 | 공통 의미이므로 유지 |
| 소재·혼방 원문, 두께 1~5, 메모 | 기존 의미·사용자 의도를 유지. 두께의 카테고리별 예시는 바뀌지만 저장 수치를 자동 변환하지 않음 |
| 기존 사진·새로 선택한 사진 | 유지. 분류 변경으로 삭제·교체·재압축·업로드하지 않음 |

호환성 판단은 기존 `garment_options.dart`의 추천을 재사용한다. 사용자 지정 문자열의 정확한 용도는 코드만으로 확정할 수 없으므로 잘못된 값이라고 단정하지 않는다. 대신 기존 의류를 편집할 때는 해당 임시 값을 비워도 되는지 확인받는다. 원본의 사용자 지정 문자열을 자동 수정하거나 일괄 변환하지 않는다.

## 신규 등록과 기존 수정

- **신규 등록:** 카테고리를 바꾸면 맞지 않는 종류·핏만 바로 초기화하고 안내를 표시한다. 추천 목록과 설명·실루엣은 새 분류 기준으로 갱신한다.
- **기존 의류 로딩:** 모든 저장 값을 그대로 폼에 불러온다. 진입·뒤로 가기·카테고리를 건드리지 않은 저장으로 자동 정리하지 않는다. 기존 무변경 저장 경로도 유지한다.
- **기존 의류의 카테고리 변경:** 초기화 대상이 있으면 카테고리 이름과 정리할 필드·값을 확인 창에 표시한다. 확인 전까지 드롭다운의 값도 이전 카테고리로 유지한다. 취소·창 닫기 시 기존 카테고리와 입력 상태를 그대로 유지한다. 확인 후에는 편집 중인 종류·핏만 정리한다.
- **기존 의류의 세부 종류 변경:** 현재 핏이 새 종류와 호환되면 유지한다. 호환되지 않으면 종류 변경과 핏 초기화를 하나의 확인 절차로 처리한다. 취소하면 적용 중이던 종류와 핏으로 돌아간다.
- **분류를 다시 되돌리는 경우:** 확인해서 비운 값은 자동 복원하지 않는다. 카테고리별 숨겨진 복원 캐시를 만들지 않는다. 편집을 저장하지 않고 닫았다가 다시 열면 저장 원본을 다시 읽으므로 원래 값이 나타난다.

카테고리의 내부 값과 화면 표시가 어긋나지 않도록 제어형 `DropdownButton`과 일반 `FormField`를 사용한다. 선택 제안만으로 폼의 실제 카테고리를 먼저 바꾸지 않는다.

## 직접 입력과 저장 직전 검증

직접 입력은 글자마다 확인 창을 띄우지 않는다. 입력 중 텍스트와 적용된 세부 종류를 분리하고 **종류 적용** 버튼 또는 Enter로 확정한다. 추천 칩은 즉시 같은 확정 절차를 거친다. 핏 안내는 적용된 종류를 기준으로 표시한다.

저장 버튼은 미적용 직접 입력부터 확정·검증한다. 필요한 초기화 확인을 취소하면 저장 전체를 중단한다. 다른 카테고리에만 있는 표준 종류를 새로 잘못 입력한 경우 오류를 표시하고 적용·저장을 진행하지 않는다. 이미 저장된 사용자 지정/과거 값은 최초 로딩이나 무변경 경로에서 임의로 삭제하지 않는다.

확인 후에는 적용된 종류, 직접 입력 컨트롤러, 핏을 함께 갱신한다. 직렬화는 적용된 값만 사용하며 이전 컨트롤러 값이나 카테고리별 캐시를 섞지 않는다. 사용자 지정 핏을 현재 분류에 직접 새로 입력하는 기존 기능과 추천 외 핏의 저장 확인은 유지한다.

실제 저장 호출은 기존 방식이다. 서버는 원래 읽었던 `original` 객체를 그대로 `saveWithOriginal`에 전달한다. 로컬은 사진을 바꾸지 않았으면 `imageBytes: null`로 정보만 저장한다. ID·생성일·서버 UUID/local_id 구분과 revision 충돌 처리도 유지한다.

## 검증과 테스트 중 수정

새 테스트는 합성 코트와 작은 생성 이미지, 메모리 저장소만 사용한다. 신규 아우터→신발, 수정 코트→스커트→신발, 확인 취소, 직접 입력 미적용 상태의 취소·저장, 호환 핏 유지, 사용자 지정 원본의 편집 취소 후 재열기, 숨겨진 이전 값 없이 직렬화·저장, 공통 필드 보존, 서버 원본 revision 객체 전달을 검사한다. 긴 사용자 지정 값과 글자 크기 1.5배를 3개 테마의 360px 화면에서 검사한다.

초기 테스트에서 `DropdownButtonFormField`의 `didChange`가 `onChanged`를 다시 호출해 재귀하는 오류를 발견했다. 내부 값을 되돌리는 방식 대신 확인 완료 값만 표시하는 제어형 드롭다운으로 수정했고, 확인·취소 테스트를 다시 통과시켰다. 테스트 보조 코드의 필드 탐색 오류도 수정했다. 이를 위해 저장소나 SQL을 수정하지 않았다.

## 데이터 보호

모델·옵션·DTO·저장소·사진 처리·SQL·Edge Functions 등 기존 보호 대상 소스 **34개**의 전후 해시가 동일했다. 모델 v2 변경, DB 마이그레이션, 일괄 수정은 없다.

실제 8080 IndexedDB, 기존 옷 3벌과 사진, 서버 아이보리 셔츠·고양이·브라운 코트와 사진에 접근하거나 쓰지 않았다. 서버 DB/Storage API 호출이나 초기화도 없다. SQL·RLS·Storage 정책·Edge Functions, JPEG restart 처리, 설정 저장소는 변경하지 않는다. 클라우드 연결·배포·Git commit/push를 하지 않는다.

## Edge 확인 방법

컨트롤러 상태가 추가되었으므로 실행 중인 Flutter 앱을 **완전히 재시작**한다. 브라우저 데이터는 지우지 않는다.

```powershell
flutter run -d edge --web-hostname=localhost --web-port=8081 --dart-define-from-file=config/supabase.crud.local.json
```

새 등록 폼에서 아우터→코트와 핏을 선택한 후 신발로 바꾸면 종류·핏만 비워져야 한다. 기존 의류 수정에서는 확인 창에서 취소하면 카테고리·종류·핏이 그대로여야 하고, 확인하면 안내한 임시 값만 비워져야 한다. 다시 이전 카테고리로 바꿔도 값은 자동 복원되지 않아야 한다.

실제 브라운 코트의 저장 데이터를 바꾸고 싶지 않다면 확인 후에도 **저장하지 않고 뒤로 이동**한다. 재진입하면 저장된 원래 코트와 핏을 확인할 수 있다. 저장까지의 수동 테스트는 별도 합성 의류로 진행한다.
